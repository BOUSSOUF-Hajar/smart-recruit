## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Filtre par rôle, entreprise ou état, recherche par nom ou email, liste paginée | `AdminUsersIT.listFiltersByCompanyRoleStateAndTextWithoutAccents` (« ELODIE berard » trouve « Élodie Bérard », tri par nom) ; `UserCriteriaTest` ; `user-list.page.spec` (filtres lus dans l'URL) |
| Désactivation : sessions révoquées immédiatement, la requête suivante échoue | `disablingRevokesSessionsAtTheNextRequestAndEnablingRestoresLogin` : le token encore valide reçoit `401 AUTHENTICATION_REQUIRED` tout de suite, connexion refusée, refresh tokens révoqués, audit `USER_DISABLED` ; `JwtSecurityTest.aTokenOfAnOlderSessionVersionIsRefusedWithoutBeingCalledExpired` |
| Son propre compte ou le dernier admin actif → `LAST_ADMIN` | `anAdminCannotDisableHimself` ; `theLastActiveAdminSurvivesTwoSimultaneousDeactivations` (deux admins se désactivent mutuellement au même instant : un seul y parvient) |
| Le rôle ne se modifie pas (G-3) | `updateChangesNameAndCompanyNeverTheRoleAndRevokesSessionsOnCompanyChange` (un `"role":"ADMIN"` envoyé est ignoré) ; le formulaire affiche le rôle sans champ |

Compléments : changer l'entreprise d'un recruteur ferme ses sessions (son token portait l'ancienne entreprise) ; un recruteur d'une entreprise désactivée ne peut pas être réactivé (`aRecruiterOfAnInactiveCompanyCannotBeEnabled`) ; version obsolète → `409 CONCURRENT_MODIFICATION`.

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Version de session dans le token (claim `sv`), comparée en mémoire à chaque requête | Liste noire des tokens ; lecture de `app_user.enabled` à chaque requête ; attendre l'expiration (15 min) | Une désactivation doit couper tout de suite (critère) ; sans requête SQL par appel ; un seul entier par compte révoqué |
| Mise à jour du registre **après validation** de la transaction | Mise à jour immédiate | Une désactivation annulée (erreur plus loin) ne doit couper personne |
| Refus en `AUTHENTICATION_REQUIRED`, pas `AUTH_TOKEN_EXPIRED` | Code « expiré » | Le frontend ne tente pas de renouveler une session révoquée, il déconnecte |
| Verrou `SELECT … FOR UPDATE` sur les admins actifs (RG-29) | Simple `count(*)` | Deux admins qui se désactivent mutuellement en même temps passeraient tous deux le comptage |
| Filtre par entreprise et nom de l'entreprise via `RecruiterAffiliations`, implémentée par le module Entreprises | Jointure SQL de `identity` vers `recruiter_profile` | Identité reste le module le plus bas : il ne connaît pas les tables des autres (même inversion que `RecruiterCompanyLookup`) |
| Recherche `lower(immutable_unaccent(prénom nom))` | `lower` seul | En collation C, `lower` ne connaît que l'ASCII : les accents d'abord |

## 4. Limite assumée

Le registre des versions est en mémoire, rechargé au démarrage. Avec plusieurs instances du backend, chacune ne verrait que ses propres révocations jusqu'à son redémarrage : il faudrait un canal partagé (Redis, `LISTEN/NOTIFY` de PostgreSQL). Documenté dans la classe ; l'application tourne sur une instance (architecture §9).

## 6. Questions d'entretien

**« Un JWT est sans état : comment le révoquer avant son expiration ? »** On réintroduit un minimum d'état : une version de session par compte, incrémentée à la désactivation. Le token porte la version de son émission ; le validateur refuse une version dépassée. C'est un entier en mémoire par compte révoqué, pas une liste de tokens.

**« Pourquoi verrouiller pour compter les admins ? »** Sans verrou, deux transactions concurrentes lisent chacune « 2 admins actifs », et chacune désactive l'autre. Le `FOR UPDATE` sérialise : la seconde relit après la première et ne voit plus qu'un admin.
