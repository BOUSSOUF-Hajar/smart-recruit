# US-52 — Tracer les actions sensibles

Phase 2 · MUST · 3 points · dépend de US-02 · réf. F-AUDIT-01, RG-24

## 1. Objectif et critères

Un composant unique, `AuditRecorder`, que les autres modules appellent pour écrire dans le journal d'audit. Aucune action n'est encore auditée : la connexion (US-07) sera la première.

| Critère d'acceptation | Preuve |
| --- | --- |
| Entrée écrite avec date, utilisateur, action, ressource, IP et résultat, en cas de succès comme d'échec | `AuditRecorderIT.writesDateActorActionResourceIpAndResult`, `failuresAreRecordedToo` |
| Si l'écriture d'audit échoue, l'action métier est annulée | `whenAuditWriteFailsTheBusinessActionIsCancelled` |
| Ni mot de passe, ni token, ni contenu de CV dans une entrée | `sensitiveDataIsRefused`, `AuditDetailsPolicyTest` |

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| `record` en `Propagation.MANDATORY` | `REQUIRED` | Appelé hors transaction, il échoue au lieu d'écrire une trace d'une action qui n'existe pas dans la même unité de travail |
| `recordIndependently` en `REQUIRES_NEW` | Un seul mode | Une connexion refusée lève une exception qui annule la transaction : sa trace doit pourtant rester |
| `JdbcClient` (SQL direct) | Entité JPA `AuditLog` | Table en ajout seul, sans cycle de vie ; colonnes `INET` et `JSONB` écrites simplement avec un `cast` ; même transaction que JPA |
| Garde-fou sur les clés des détails | Confiance dans les développeurs | Une fuite de mot de passe dans un journal conservé 12 mois est grave ; l'erreur doit apparaître en test |
| Clé étrangère `actor_id` ajoutée en US-06 | Tout créer maintenant | La table `app_user` n'existe pas encore |
| IP via `getRemoteAddr()` | Lire `X-Forwarded-For` à la main | Un en-tête se falsifie ; derrière Nginx, Spring le traitera proprement avec `server.forward-headers-strategy` (phase 11) |

## 4. Utilisation (exemple pour US-07)

```java
@Transactional
public TokenPair login(LoginRequest request) {
    User user = users.findByEmail(request.email()).orElse(null);
    if (user == null || !user.canLogIn(passwordEncoder, request.password())) {
        audit.recordIndependently(AuditEvent.failure("LOGIN").by(user == null ? null : user.getId(), request.email()));
        throw new AuthenticationFailedException();
    }
    audit.record(AuditEvent.success("LOGIN").by(user.getId(), user.getEmail()));
    return tokens.issue(user);
}
```

## 5. Erreurs probables

| Symptôme | Cause | Solution |
| --- | --- | --- |
| `IllegalTransactionStateException: No existing transaction found` | `record` appelé hors `@Transactional` | Annoter la méthode de service, ou utiliser `recordIndependently` |
| `IllegalArgumentException: Donnée sensible interdite…` | Une clé de détail ressemble à un secret | Retirer la donnée ; ne jamais renommer la clé pour contourner |
| `NullPointerException` dans `AuditEvent.with` | Valeur `null` dans les détails | Ne pas ajouter de détail sans valeur |

## 6. Questions d'entretien

**« Quelle différence entre l'audit et les logs ? »** Les logs servent au diagnostic technique, ont une durée de vie courte et peuvent être perdus. L'audit est une donnée métier : en base, dans la même transaction que l'action, consultable par l'admin, conservée 12 mois.

**« Pourquoi écrire l'audit dans la même transaction ? »** Pour qu'il ne puisse pas exister d'action sans trace, ni de trace sans action. Si l'insertion échoue, toute l'action est annulée.

**« Et pour une tentative de connexion échouée ? »** L'action est un échec, donc annulée ; la trace doit pourtant rester. D'où `REQUIRES_NEW`, qui écrit dans une transaction indépendante.
