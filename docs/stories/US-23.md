# US-23 — Cycle de vie d'une offre

Phase 5 · MUST · 5 points · dépend de US-21 · réf. F-JOB-03, RG-18, RG-19

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| DRAFT complète, expiration future ≤ 180 jours → PUBLISHED, `publishedAt` = maintenant | `JobOfferLifecycleTest.publicationSetsTheDatesAndExpiresAtEndOfDayInTheCompanyTimezone` ; `JobOfferIT.fullLifecycle` |
| PUBLISHED avec candidatures → retour en brouillon refusé | `publishedOfferWithApplicationsCannotGoBackToDraft` (le service interroge `JobApplicationStats`, implémentée en phase 6 ; absente → 0) |
| Réouverture avec expiration passée → refus | `closedOfferCannotBeReopenedWithAPastExpiry` ; `reopeningKeepsTheFirstPublicationDate` |
| Suppression d'une offre non DRAFT → `RESOURCE_IN_USE`, archivage proposé | `onlyDraftsCanBeDeleted` ; l'écran ne propose « Supprimer » qu'en brouillon (`availableActions`) |
| Chaque transition du diagramme testée | `onlyTheTransitionsOfTheStateDiagramAreAllowed` : matrice de **24 cas** (4 statuts × 6 actions) |
| (ajout) Raisons de refus groupées | `publicationLimitsAreReportedTogether`, `publicationRulesAreExplained` : 422 `JOB_NOT_PUBLISHABLE` avec `reasons` (`EXPIRY_IN_PAST`, `EXPIRY_TOO_FAR`, `NO_REQUIRED_SKILL`), traduites par `PUBLICATION_REASON_LABELS` |

## 2. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Transitions comme méthodes du domaine (`publish`, `close`…) | Machine à états générique, `setStatus` | Chaque transition a ses règles ; une méthode par transition est lisible et testable sans Spring |
| Actions REST `POST /jobs/{id}/publish` | `PATCH {status}` | Une intention par endpoint ; corps propre à l'action (date d'expiration) ; la matrice de sécurité les liste |
| Expiration = fin de journée (23:59:59) dans le fuseau de l'entreprise | Minuit UTC | « Expire le 30 » doit vouloir dire « toute la journée du 30 » pour le recruteur |
| Expiration calculée à la lecture (`expires_at > now()`) | Tâche planifiée qui passe les offres en CLOSED | Pas de décalage entre l'heure et le batch ; le statut reste un choix humain |
| Toutes les raisons de refus renvoyées ensemble | Première erreur seulement | Le recruteur corrige tout d'un coup |

## 3. Note sur le fuseau marocain

La tzdata 2026e du JDK 25 place `Africa/Casablanca` en UTC+0 de façon permanente depuis fin 2026 (au lieu du UTC+1 en vigueur auparavant hors ramadan). Les tests utilisent donc un **décalage fixe** (`ZoneOffset.ofHours(1)`) pour vérifier la règle « fin de journée dans le fuseau donné » sans dépendre de la version des données de fuseau.

## 4. Questions d'entretien

**« Pourquoi interdire le retour en brouillon s'il y a des candidatures ? »** Un brouillon est invisible : les candidats auraient postulé à une offre qui n'existe plus pour eux. On clôture à la place.

**« Comment testez-vous qu'aucune transition interdite n'est possible ? »** Test paramétré sur le produit cartésien statuts × actions : chaque ligne indique le statut attendu ou l'erreur attendue. Ajouter une action oblige à compléter la matrice.
