# US-41 — Analyser un CV

Phase 8 · MUST · 8 points · dépend de US-31, US-40 · réf. F-AI-01, F-AI-02, RG-27, analyse fonctionnelle §3.5 et §4.4

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Lancement → 202 avec un identifiant de tâche, indicateur de progression | `AiIT.analysisIsAsynchronousTraceableAndFedWithPseudonymizedText` (202, `Location`) ; `AiApi.watch` (spec : toutes les 3 s jusqu'à l'état final) ; barre de progression et annonce `LiveAnnouncer` |
| Compétences avec extrait justificatif, expériences, formations, langues, synthèse ≤ 600 caractères | Même test ; `ResumeExtraction` (Bean Validation) et schéma `resume-extraction-v1.schema.json` |
| Réponse hors schéma → une nouvelle tentative, puis FAILED `AI_INVALID_RESPONSE` | `OllamaAIServiceTest.anInvalidAnswerIsRetriedOnce`, `twoInvalidAnswersFailWithAiInvalidResponse` ; `AiIT.failuresEndTheTaskWithAnExplicitCode` |
| PDF scanné → « CV non analysable automatiquement » | `AiIT.scannedResumeIsNotAnalysableButMatchingStillWorksFromTheProfile` (`FILE_UNREADABLE`) ; message affiché par `AiPanel` |
| Redémarrage pendant une analyse → tâche orpheline FAILED | `AiIT.aRequestWhileATaskIsRunningReturnsThatTask` (`AiTaskStore.failOrphans`, appelé au démarrage par `ApplicationReadyEvent`) |
| Résultat rattaché à la version du CV, avec modèle, version du prompt, date et demandeur | Même premier test (`resume_analysis` : CV de la candidature, modèle, `resume-extraction-v1`, empreinte SHA-256 du texte envoyé ; `ai_task.requested_by`) |
| (ajout) Double clic → la tâche en cours est renvoyée | `aRequestWhileATaskIsRunningReturnsThatTask` |

## 2. Déroulé

1. `POST /applications/{id}/ai/resume-analysis` : contrôle d'entreprise, limite de 10 demandes par minute, tâche PENDING, historique `AI_ANALYSIS_REQUESTED`, audit — une transaction.
2. Après le commit (`@TransactionalEventListener(AFTER_COMMIT)`), la tâche part sur l'exécuteur `aiExecutor` (2 threads, file de 50 ; file pleine → FAILED).
3. `AiTaskWorker`, sans transaction : RUNNING (transaction courte) → texte du PDF (PDFBox) → pseudonymisation → modèle → rattachement des compétences au référentiel (noms et alias) → enregistrement et DONE (transaction courte).

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Trois temps de transaction | Une transaction autour de l'appel | Deux minutes d'appel tiendraient une connexion du pool (architecture backend) |
| Soumission après commit | Soumission immédiate | Le thread d'arrière-plan pourrait ne pas encore voir la tâche |
| Résultats en JSONB via JDBC | Entités JPA et tables éclatées | Documents produits et lus d'un bloc, jamais modifiés ; aucune requête n'en filtre le contenu |
| Analyse rattachée au CV (pas à l'offre) | Analyse par candidature | Un même CV envoyé à plusieurs offres n'est analysé qu'une fois par version de prompt |
| Verrou optimiste sur `ai_task` | Aucun | Deux exécuteurs ne peuvent pas prendre la même tâche |

## 4. Questions d'entretien

**« Que se passe-t-il si l'application redémarre pendant une analyse ? »** Au démarrage, toute tâche PENDING ou RUNNING passe FAILED : sans ce rattrapage, l'écran attendrait indéfiniment. Le recruteur relance.

**« Pourquoi pas une file de messages ? »** Une table et un pool de deux threads suffisent pour quelques analyses par heure (décision G-7). Une file deviendrait utile avec plusieurs instances du backend.
