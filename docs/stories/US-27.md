# US-27 — Postuler

Phase 6 · MUST · 5 points · dépend de US-17, US-26 · réf. F-APP-01, RG-09 à RG-12, analyse fonctionnelle §3.3

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Offre ouverte, profil minimal, CV actif → SUBMITTED, CV actuel figé, première entrée d'historique | `CandidateApplicationIT.applicationIsSubmittedWithTheCurrentResumeFrozenAndAFirstHistoryEntry` (un nouveau CV téléversé ensuite ne change pas `resume_id`) ; `ApplyDialog` spec |
| Profil incomplet → `PROFILE_INCOMPLETE` avec la liste des manques | `incompleteProfileListsWhatIsMissing` (`missing: [headline, skills, resume]`) ; `profileGaps` spec ; liens vers l'onglet du profil (`/candidate/profile?tab=N`) |
| Candidature existante → `APPLICATION_ALREADY_EXISTS` | `secondApplicationIsRefusedWithALinkToTheFirst` : la réponse porte `applicationId`, le dialogue mène à la candidature (scénario A2) |
| Deux requêtes simultanées → une seule candidature | `concurrentApplicationsCreateOnlyOne` : 4 requêtes parallèles, exactement un 201 et des 409 |
| Offre clôturée entre l'affichage et la confirmation → `JOB_NOT_OPEN` | `closedOrUnknownJobsDoNotAcceptApplications` (et 404 pour une offre inconnue) |

## 2. Fichiers

Backend : `V11__application.sql` ; module `application` : `api/ApplicationStatus`, `ApplicationSubmitted`, `domain/Application`, `application/ApplicationService.apply`, `ApplicationHistoryListener`, `infrastructure/ApplicationConstraints`, `web/CandidateApplicationController` ; `candidate/api/CandidateDirectory` (+ `ApplicationReadiness`) et `candidate/application/CandidateDirectoryService` ; `job/api/JobCatalog` (+ `JobReference`) et `job/application/JobCatalogService`.
Frontend : `features/candidate/applications/components/apply-dialog.ts`, `data-access/candidate-applications.{api,models}.ts`, bouton « Postuler » de `job-detail.page.ts`, paramètre `tab` du profil.

## 3. Déroulé (une transaction)

1. `JobCatalog.find` : offre inconnue → 404 ; non ouverte → 409 `JOB_NOT_OPEN`.
2. Candidature déjà existante → 409 avec son identifiant (message clair dans le cas courant).
3. `CandidateDirectory.readiness` : RG-09 vérifié par le module Candidats, qui renvoie aussi le CV actif.
4. `saveAndFlush` : l'index `uk_application_job_candidate` arrête un éventuel doublon concurrent **dans** la transaction ; `KnownConstraint` le traduit en `APPLICATION_ALREADY_EXISTS`.
5. Événement `ApplicationSubmitted` → `ApplicationHistoryListener` écrit l'entrée CREATED dans la même transaction ; audit `APPLICATION_SUBMITTED`.

## 4. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Garantie d'unicité par l'index, vérification préalable pour le message | Vérification seule ; verrou applicatif | Deux requêtes passent toutes deux la vérification ; seul l'index est atomique |
| `saveAndFlush` | `save` | Sans flush, la violation surgit au commit, après la méthode, hors du flux métier |
| Le module Candidats décide du profil minimal (`ApplicationReadiness`) | Candidatures lit les tables du profil | La règle vit à côté des données ; les codes (`headline`, `resume`…) sont ceux de la complétude, donc déjà traduits par le frontend |
| Récapitulatif avant confirmation (F-APP-01 étape 2) | Postuler au premier clic | Le candidat voit quel CV part ; il sait qu'il restera attaché à la candidature |
| `JOB_NOT_OPEN` même pour un brouillon | 404 pour un brouillon | Identifiants UUIDv7 non devinables ; un code unique simplifie le frontend |

## 5. Erreurs probables

- Oublier le flush : la violation d'unicité devient un 500 au commit.
- Lire le CV actif après l'insertion : course avec un remplacement de CV. Il est lu une fois, puis figé.
- Une suppression de CV pile au même moment fait échouer l'insertion sur `fk_application_resume` : traduite en `CONCURRENT_MODIFICATION` (« votre CV vient de changer »).

## 6. Questions d'entretien

**« Comment avez-vous testé la concurrence ? »** Quatre threads attendent un `CountDownLatch`, puis envoient la même candidature. On vérifie un seul 201 et une seule ligne en base. Le test échouerait sans l'index.

**« Pourquoi pas `SELECT ... FOR UPDATE` ? »** Il n'y a rien à verrouiller avant que la ligne existe. L'index unique est la seule protection naturelle contre une insertion en double.
