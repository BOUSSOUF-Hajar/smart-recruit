# US-47 — Créer un compte recruteur ou admin (+ US-49 partiel)

Phase 5 · MUST · 3 points · dépend de US-10 · réf. F-AUTH-05, RG-04

Avancée en phase 5 parce que les offres ont besoin de recruteurs rattachés à une entreprise. US-49 (gérer les entreprises) est livrée **en partie** : création et liste ; modification et désactivation en cascade ont été livrées en phase 10 ([US-49](US-49.md)).

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Recruteur créé avec un mot de passe temporaire aléatoire, affiché une seule fois, marqué « à changer » | `AdminAccountsIT.recruiterGetsATemporaryPasswordShownOnceAndMustChangeIt` (réponse `no-store`, connexion avec le mot de passe temporaire → `mustChangePassword: true` ; le blocage `PASSWORD_CHANGE_REQUIRED` est celui de US-08, et `StaffSessions.recruiter` enchaîne le changement) ; `TemporaryPasswordsTest` ; `TemporaryPasswordDialog` spec |
| Entreprise inactive ou email existant → refus, rien n'est créé | `inactiveCompanyRefusesNewRecruitersAndNothingIsCreated`, `existingEmailIsRefused` ; `CreateUserPage` spec (erreur sous le champ email) |
| Rôle et entreprise cohérents | `roleAndCompanyMustMatch` (candidat interdit, recruteur sans entreprise, admin avec entreprise) ; `staff-form.spec` (l'entreprise est retirée pour un admin) |
| Création auditée | Même test : ligne `USER_CREATED` dans `audit_log` |
| Réservé aux admins | `onlyAdminsManageAccounts`, `SecurityMatrixIT` (`POST /admin/users`, `/admin/companies`) |
| US-49 : nom d'entreprise unique sans tenir compte de la casse | `companyNamesAreUniqueRegardlessOfCase` (index `uk_company_name` sur `lower(name)` → `RESOURCE_IN_USE`) |

## 3. Déroulé

1. `POST /api/v1/admin/users` : `StaffAccountService` vérifie rôle/entreprise et l'unicité de l'email, crée l'utilisateur avec un mot de passe temporaire haché, publie `StaffAccountCreated`.
2. `StaffAccountListener` (module `company`, **même transaction**) contrôle que l'entreprise existe et est active puis crée le `RecruiterProfile`. S'il lève une exception, toute la transaction est annulée : aucun compte orphelin.
3. La réponse `201 {user, temporaryPassword}` part avec `Cache-Control: no-store`. Le mot de passe n'est jamais journalisé ni relisible.
4. Le frontend l'affiche dans un dialogue non fermable par clic extérieur (`disableClose`), avec un bouton copier, puis vide le formulaire.

## 4. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Événement synchrone `StaffAccountCreated` écouté par `company` | `identity` appelle `company` directement | `company` dépend déjà d'`identity` (lookup recruteur → entreprise) ; un appel inverse créerait un cycle que Spring Modulith refuse |
| `@EventListener` synchrone dans la transaction | `@ApplicationModuleListener` (asynchrone, après commit) | Le refus d'une entreprise inactive doit annuler la création du compte |
| Mot de passe temporaire `XXXX-XXXX-XXXX-XXXX`, alphabet sans `0/O`, `1/I/L` (`SecureRandom`) | Lien d'activation par email | Pas de serveur de mail en phase 5 ; ~78 bits d'entropie, lisible au téléphone ; l'email arrivera avec les notifications |
| Changement obligatoire à la 1re connexion (filtre `PasswordChangeRequiredFilter` existant, US-08) | Mot de passe définitif choisi par l'admin | L'admin ne connaît jamais le mot de passe final du recruteur |
| Unicité du nom par index sur `lower(name)` | Vérification applicative seule | Seule la base garantit l'unicité face à deux requêtes simultanées |

## 6. Erreurs probables

- Oublier `no-store` : un proxy ou le cache du navigateur pourrait conserver le mot de passe.
- Écouter l'événement en asynchrone : le compte serait créé même pour une entreprise inactive.
- Afficher le mot de passe dans un snackbar : il disparaît avant d'avoir été noté.

## 7. Questions d'entretien

**« Pourquoi un événement plutôt qu'un appel de service ? »** Pour respecter le sens des dépendances entre modules : `identity` ne connaît pas `company`. L'événement est synchrone et transactionnel, donc le comportement est celui d'un appel direct, sans le couplage.

**« Que se passe-t-il si l'admin ferme le dialogue sans noter le mot de passe ? »** Il ne peut pas le relire (seul le hash est stocké). La réinitialisation par l'admin fait partie de US-48 (phase 9) ; en attendant, le recruteur passe par « mot de passe oublié » quand il existera, ou l'admin recrée le compte.
