# US-51 — Fusionner des compétences

Phase 10 · SHOULD · 5 points · dépend de US-15 · réf. F-ADM-05

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| « springboot » fusionné dans « Spring Boot » : profils et offres pointent vers la cible, la source devient un alias | `AdminReferentialIT.mergingMovesProfilesAndJobsKeepsTheHighestLevelAndLeavesAnAlias` (3 références reportées, source supprimée, « SpringBoot » saisi ensuite par un candidat renvoie la cible) |
| Profil qui avait les deux → un seul exemplaire, au niveau le plus élevé | Même test : EXPERT + BEGINNER → EXPERT ; l'offre qui demandait la source (requise, ADVANCED) et la cible (souhaitée) garde la cible requise au niveau ADVANCED |
| Fusion auditée | Même test : `SKILL_MERGED` avec le nom de la source, le nom de la cible et le nombre de références |

Compléments (`mergeAndRenameGuardAgainstMistakes`) : fusionner une compétence avec elle-même → 400 ; renommer vers un nom déjà pris → 409 avec l'identifiant de l'autre compétence (« fusionnez plutôt ») ; corriger une faute garde l'ancienne orthographe comme alias ; une cible désactivée est refusée.

## 2. Fichiers

- Backend : `referential/application/AdminSkillService`, `web/AdminSkillController` ; `Skill.rename/deactivate/activate`, `SkillAlias.of`, `SkillAliasRepository.reassign` ; `ReferentialUsage.reassignSkill`, implémentée par `job/infrastructure/JobReferentialUsage` et `candidate/infrastructure/CandidateReferentialUsage`.
- Frontend : `skills/skill-list.page.ts` (recherche par nom ou alias, utilisations, alias), `components/merge-skill-dialog.ts` (cible choisie dans le référentiel, sans création, avec le résumé de ce qui va se passer).

## 3. Déroulé de la fusion (une transaction)

1. Chaque module qui référence des compétences reporte ses lignes : d'abord la fusion des doublons (`UPDATE … FROM` qui garde le niveau le plus élevé via `array_position` sur la liste ordonnée des niveaux), puis la suppression des lignes source en double, puis le report des autres.
2. Les alias de la source passent à la cible ; le nom normalisé de la source devient un alias.
3. La source est supprimée (plus aucune clé étrangère ne la désigne).
4. Audit `SKILL_MERGED`.

## 4. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| SQL direct dans chaque module propriétaire de ses tables | Chargement des profils et offres en JPA | Une fusion peut toucher des centaines de lignes : trois requêtes par module au lieu de N entités |
| Supprimer la source et créer un alias | Garder la source désactivée | L'alias suffit à reconnaître l'ancien nom (autocomplétion, extraction IA, `getOrCreate`) ; une compétence fantôme brouillerait le référentiel |
| Requise l'emporte sur souhaitée dans une offre | Garder la ligne de la cible telle quelle | Ne jamais affaiblir une exigence du recruteur |
| Résultats IA déjà calculés laissés tels quels | Les réécrire | Ce sont des traces historiques (RG-27) ; le prochain matching utilisera la cible |

## 5. Question d'entretien

**« Que se passe-t-il pour un profil qui avait les deux compétences ? »** La clé primaire `(candidate_id, skill_id)` interdit deux lignes pour la cible. On met d'abord à jour la ligne cible avec le maximum des deux niveaux et des deux durées, on supprime la ligne source, puis on reporte les profils qui n'avaient que la source.
