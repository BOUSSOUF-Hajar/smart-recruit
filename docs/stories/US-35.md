# US-35 — Planifier un entretien

Phase 7 · MUST · 5 points · dépend de US-32 · réf. F-INT-01, RG-21, RG-32

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Candidature en INTERVIEW, date future, durée, type, au moins un participant de l'entreprise → SCHEDULED, dans l'historique | `InterviewIT.interviewIsStoredInUtcAndAppearsInTheHistory` (entrée `INTERVIEW_SCHEDULED`, entretien visible dans le dossier) ; `InterviewDialog` spec |
| VIDEO sans lien https, ON_SITE sans adresse → refus | `locationAndParticipantsAreValidated` (`meetingUrl`, `address`, participant d'une autre entreprise sur `participantIds`, date passée sur `startsAt`) ; `InterviewTest.locationDependsOnTheTypeAndAllErrorsAreReportedTogether` ; validateurs conditionnels du formulaire ; contraintes `ck_interview_video_url`, `ck_interview_address` |
| Candidature pas en INTERVIEW → `INTERVIEW_NOT_ALLOWED` | `interviewNeedsAnApplicationAtTheInterviewStage` ; le bouton « Planifier » n'apparaît qu'au statut Entretien |
| 10 h à Casablanca → stocké en UTC, réaffiché à 10 h dans le même fuseau | Même premier test (10 h à UTC+1 envoyé avec son décalage, renvoyé en `Z`) ; `interview.spec.ts` (`localInputToIso` / `isoToLocalInput`, aller-retour sans décalage) |

## 2. Fichiers

Backend : `V12__interview_and_note.sql` ; module `interview` : `domain/Interview`, `InterviewPlan`, `InterviewType`, `InterviewStatus`, `FeedbackRating`, `infrastructure/InterviewRepository`, `InterviewCriteria`, `application/InterviewService`, `InterviewQueryService`, `web/RecruiterInterviewController`, `InterviewRequests`, `InterviewResponses` ; `application/api/ApplicationDirectory`, `ApplicationRef`, `InterviewHistory` (+ implémentations dans le module Candidatures) ; `company/api/RecruiterSummary`, `CompanyDirectory.recruitersOf`, `company/web/CompanyRecruitersController`.
Frontend : `shared/models/interview.ts`, `features/recruiter/interviews/` (dialogues, carte, actions, agenda), onglet Entretiens du dossier.

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| `startsAt` reçu en `OffsetDateTime`, stocké en `Instant` (`timestamptz`) | `LocalDateTime` + fuseau de l'entreprise | Le décalage voyage avec la valeur ; aucune ambiguïté au changement d'heure ; le navigateur affiche dans le fuseau de chacun (RG-32) |
| Conversion locale ↔ UTC dans deux fonctions pures (`localInputToIso`, `isoToLocalInput`) | Bibliothèque de dates | `datetime-local` + `Date` suffisent ; fonctions testées |
| Toutes les erreurs de champ ensemble (`InterviewPlan.validate`) | Première erreur seulement | Le recruteur corrige tout en une fois |
| `company_id` et `job_offer_id` copiés dans `interview` | Jointure vers `application` | L'agenda de l'entreprise se lit dans le module ; ces valeurs ne changent jamais (écart documenté au modèle de données) |
| Historique écrit par un appel à `InterviewHistory` (API de Candidatures) | Événements d'entretien écoutés par Candidatures | Entretiens dépend déjà de Candidatures ; l'inverse créerait un cycle que Spring Modulith refuse |
| Participants vérifiés via `CompanyDirectory.recruitersOf` | Clé étrangère seule | La FK garantit un compte, pas un recruteur de la même entreprise |

## 4. Questions d'entretien

**« Comment gérez-vous les fuseaux horaires ? »** Stockage en UTC, transport en ISO 8601 avec décalage, affichage dans le fuseau du navigateur. Le serveur ne devine jamais un fuseau.

**« Pourquoi Casablanca est-il un bon cas de test ? »** Son décalage change (ramadan, et la tzdata 2026e le met en UTC+0 permanent) : c'est exactement le cas où stocker des heures locales casse.
