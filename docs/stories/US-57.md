# US-57 — Tests de bout en bout

Phase 11 · SHOULD · 5 points · dépend de US-32 · réf. section 19 du prompt

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Inscription puis candidature | `e2e/candidate-journey.e2e.ts` : création du compte, titre, une compétence choisie dans l'autocomplétion, CV PDF généré à la volée, candidature, retour dans « Mes candidatures » avec le statut « Envoyée » |
| Connexion recruteur puis changement de statut | `e2e/recruiter-workflow.e2e.ts` : recruteur de démo, liste filtrée sur « Reçue », dossier, « Faire avancer » → présélection, vérification du statut et de l'historique |
| Accès refusé à l'espace d'un autre rôle | `e2e/access-control.e2e.ts` : un candidat renvoyé vers son espace depuis `/recruiter` et `/admin`, puis `403` de l'API d'administration avec son propre jeton ; un visiteur renvoyé vers la connexion |
| Les tests tournent sur `main` dans la pipeline | Job `e2e` de la CI, sur chaque pull request et sur `main` |

Garde-fou commun (`e2e/support.ts`) : une violation de la CSP ou une erreur JavaScript non gérée fait échouer le test, même si l'écran a l'air de fonctionner.

## 2. Exécution

4 tests, 10 s, tous verts dans l'environnement de développement : frontend de production servi par la vraie configuration Nginx du projet, backend en profil `dev,demo` sur une base neuve.

```bash
cd frontend
npx playwright install chromium        # une fois
E2E_BASE_URL=http://localhost:8080 npm run e2e
```

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Trois parcours critiques, pas plus | Couvrir chaque écran | Les tests de bout en bout sont lents et fragiles ; le reste est couvert par les tests unitaires et d'intégration |
| Sélecteurs par rôle et libellé (`getByRole`, `getByLabel`) | Sélecteurs CSS | Proches de ce que voit l'utilisateur, et vérifient au passage l'accessibilité |
| Données de démo comme point de départ, comptes neufs pour l'inscription | Jeu de données propre aux tests | Les tests vérifient aussi que la démo fonctionne ; un email unique par exécution rend le test rejouable |
| PDF construit dans le test | Fichier binaire commité | Aucun binaire dans le dépôt, comme pour les tests backend |
