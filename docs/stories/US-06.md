# US-06 — S'inscrire comme candidat

Phase 3 · MUST · 5 points · dépend de US-02, US-03 · réf. F-AUTH-01, RG-01, RG-02, RG-04

## 1. Objectif et critères

Un visiteur crée un compte candidat et repart connecté. Le rôle est imposé par le serveur, le profil vide est créé dans la même transaction.

| Critère d'acceptation | Preuve |
| --- | --- |
| Compte CANDIDATE actif + profil vide + session ouverte | `AuthFlowIT.registrationCreatesACandidateWithAnEmptyProfileAndOpensASession` |
| Email déjà utilisé, quelle que soit la casse → `EMAIL_ALREADY_USED`, rien de créé | `emailIsUniqueRegardlessOfCase` ; index `uk_app_user_email` sur `lower(email)` pour le cas concurrent |
| Mot de passe < 12 caractères ou courant → champ en erreur | `weakOrInvalidRegistrationIsRejectedFieldByField`, `CommonPasswordsTest` |
| Mot de passe haché en BCrypt | même test d'inscription : `password_hash` commence par `{bcrypt}$2` |
| Rôle envoyé par le client ignoré | même test : corps avec `"role":"ADMIN"`, compte CANDIDATE |

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Pas de champ `role` dans `RegisterRequest` | Champ présent puis écrasé | Ce qui n'existe pas ne peut pas être lié par erreur (mass assignment) |
| Vérification applicative **et** index unique | L'un des deux | La vérification donne un message propre ; seul l'index résiste à deux inscriptions simultanées |
| `saveAndFlush` | `save` | L'INSERT part tout de suite : la violation d'index est levée dans le service, pas au commit après la réponse |
| Événement `CandidateRegistered` synchrone | Appel direct du module Candidats ; `@ApplicationModuleListener` asynchrone | Identité ignore Candidats (dépendance inversée) ; synchrone pour que l'inscription échoue si le profil ne peut pas être créé |
| Hibernate `@UuidGenerator(style = VERSION_7)` | `DEFAULT uuidv7()` lu après insertion | L'identifiant est connu avant l'INSERT, utile pour l'événement et l'audit |
| `@JdbcTypeCode(SqlTypes.CHAR)` sur les colonnes `CHAR(n)` | `VARCHAR` partout | Le schéma suit le modèle de données ; sans l'annotation, `ddl-auto=validate` refuse le démarrage |
| Liste locale de mots de passe courants | API « Have I Been Pwned » | Aucune dépendance réseau à l'inscription ; liste revue et versionnée |

## 4. Erreurs probables

| Symptôme | Cause | Solution |
| --- | --- | --- |
| `Schema-validation: wrong column type ... found [bpchar], but expecting [varchar(64)]` | Colonne `CHAR` sans `@JdbcTypeCode(SqlTypes.CHAR)` | Ajouter l'annotation |
| `IllegalTransactionStateException` dans le listener | Événement publié hors transaction | Publier depuis une méthode `@Transactional` |
| 500 au lieu de 409 sur un doublon concurrent | `KnownConstraint` absent ou nom d'index différent de la migration | Vérifier le nom `uk_app_user_email` |
| `ck_app_user_privacy` violée | Candidat créé sans date de consentement | Passer par `User.registerCandidate` |

## 5. Questions d'entretien

**« Comment empêchez-vous un utilisateur de s'inscrire comme admin ? »** Le DTO n'a pas de champ rôle, la fabrique `registerCandidate` fixe CANDIDATE, et un test envoie `"role":"ADMIN"` pour le prouver.

**« Pourquoi un index sur `lower(email)` alors que vous normalisez déjà en minuscules ? »** La normalisation est une règle applicative ; l'index est la garantie. Un import SQL ou un futur endpoint qui oublierait la normalisation serait quand même arrêté.

**« Pourquoi un événement plutôt qu'un appel au service Candidats ? »** Pour garder Identité indépendant : il annonce un fait, Candidats réagit. Spring Modulith vérifie qu'Identité ne dépend pas de Candidats.
