# US-44 — Tableau de bord recruteur

Phase 9 · MUST · 5 points · dépend de US-34, US-35 · réf. D8, analyse fonctionnelle §6.3

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Offres par statut, candidatures sur 7 et 30 jours, nombre en SCREENING et SHORTLISTED, entretiens des 7 prochains jours, embauches de la période, tableau par offre | `DashboardIT.recruiterSeesTheIndicatorsOfHisCompanyOnly` (chaque champ vérifié sur un jeu connu) ; `RecruiterDashboardPage` affiche chaque bloc |
| « 12 en SCREENING » mène à la liste filtrée sur ce statut | `recruiter-dashboard.page.spec.ts` : liens `?status=SCREENING`, `?status=SHORTLISTED`, `?status=HIRED`, `?submittedFrom=…`, `/recruiter/jobs?status=…`, `?jobOfferId=…&status=…` ; la liste lit ces paramètres depuis la phase 6 (`withComponentInputBinding`) |
| Les données d'une autre entreprise ne sont jamais comptées | Même test d'intégration : une seconde entreprise avec offres, candidatures, embauche et entretien, aucun chiffre ne bouge ; toutes les requêtes filtrent par `company_id` du recruteur connecté, jamais par un paramètre |
| Indicateurs en moins d'une seconde sur le volume de démonstration | Mesure ci-dessous : **14,47 ms** (somme des médianes, 10 000 candidatures) ; `SecurityMatrixIT` vérifie l'accès réservé au rôle RECRUITER |

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Calcul à la volée en SQL agrégé (`count(*) FILTER`, `GROUP BY`) | Table de statistiques tenue à jour par événements | 15 ms mesurées : une table de cumuls ajouterait une source de vérité à synchroniser pour un gain invisible |
| Module `reporting` qui lit les tables des autres modules en SQL (JdbcClient) | Une méthode de comptage par module, appelée tour à tour | Lecture seule, une requête par bloc au lieu de N appels ; exception documentée à la règle des frontières de modules, comme `RecruiterApplicationSearch` (US-30). Le module n'écrit rien et ne dépend d'aucun autre en Java |
| Embauches lues dans l'historique (`application_event`, `to_status = HIRED`) | `status = 'HIRED'` sur la candidature | L'historique donne la date du passage ; index partiel `ix_application_event_hires` (V11) |
| Une seule requête pour les quatre compteurs de candidatures (`FILTER`) | Quatre `count(*)` | Un seul parcours des candidatures de l'entreprise |
| Tableau par offre limité aux 50 offres non archivées les plus récentes (CTE), regroupé en Java | Toutes les offres | Taille de réponse bornée ; les archives restent dans la liste des offres |
| Fenêtre de 7 × 24 h glissantes côté serveur, lien vers la liste filtrée à partir de J-7 | Fenêtre en jours calendaires | Le filtre de la liste travaille en dates ; partir de J-7 garantit que la liste contient toutes les candidatures comptées (elle peut en montrer une ou deux de plus, écart documenté) |
| Chiffres cliquables via `routerLink` + `queryParams` | Gestionnaires `click` qui naviguent | Vrais liens : ouverture dans un nouvel onglet, clavier, lecteur d'écran |

## 4. Mesure de performance

```bash
createdb smartrecruit_perf   # migrations V1 à V13 appliquées
psql -d smartrecruit_perf -f backend/scripts/perf/seed-2000-jobs.sql
psql -d smartrecruit_perf -f backend/scripts/perf/seed-applications.sql
backend/scripts/perf/measure-dashboard.sh smartrecruit_perf
```

| Requête | Médiane |
| --- | --- |
| Offres par statut | 0,40 ms |
| Compteurs de candidatures (7 j, 30 j, SCREENING, SHORTLISTED) | 8,63 ms |
| Embauches sur 30 jours | 0,56 ms |
| Entretiens des 7 prochains jours | 0,47 ms |
| Tableau par offre | 4,42 ms |
| **Total** | **14,47 ms** |

Mesure sur PostgreSQL 18, conteneur de développement, cache chaud. Le seuil du critère (1 s) laisse une marge de deux ordres de grandeur.

## 6. Erreurs probables

- Compter les embauches avec `status = 'HIRED'` : une embauche ancienne compterait dans « les 30 derniers jours ».
- Lire l'entreprise depuis un paramètre de requête au lieu du jeton : fuite entre entreprises.
- Oublier `WHERE company_id` dans une sous-requête (le tableau par offre) : le test à deux entreprises le détecte.

## 7. Questions d'entretien

**« Pourquoi ne pas précalculer les statistiques ? »** Parce que la mesure dit que ce n'est pas nécessaire : 15 ms sur 10 000 candidatures. Précalculer, c'est un cache à invalider ; je le ferais le jour où la mesure le justifie, avec une vue matérialisée rafraîchie périodiquement.

**« Le module reporting lit les tables des autres : n'est-ce pas contraire à la modularité ? »** C'est une exception assumée et documentée, en lecture seule. Spring Modulith vérifie les dépendances Java, pas le SQL ; le risque est qu'une migration casse ces requêtes, et `DashboardIT` le détecte.
