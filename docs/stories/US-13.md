# US-13 — Informations de base du profil

Phase 4 · MUST · 3 points · dépend de US-10 · réf. F-CAND-01, RG-06

## 1. Objectif et critères

Le candidat renseigne son identité, son titre et son résumé depuis l'onglet « Informations » de son profil.

| Critère d'acceptation | Preuve |
| --- | --- |
| Prénom, nom, téléphone, ville, pays, titre, résumé et années enregistrés puis réaffichés | `CandidateProfileIT.basicInformationIsSavedOnTheProfileAndTheAccount` |
| Téléphone hors format international ou résumé de plus de 2 000 caractères → champ en erreur | `invalidPhoneAndTooLongSummaryAreFieldErrors` ; validateur `e164Phone` côté Angular (`forms.spec`) |
| Un autre candidat ne lit ni ne modifie mon profil (404) | Aucun identifiant dans l'URL (`/candidates/me/...`) ; pour les rubriques identifiées : `anotherCandidateCannotTouchMyExperience` |
| Aucun champ âge, photo, sexe, nationalité ou situation familiale | `ProfilePage` spec (texte de l'écran) ; DTO `UpdateProfileRequest` sans ces champs |

## 2. Fichiers

| Fichier | Rôle |
| --- | --- |
| `candidate/domain/CandidateProfile.java` | Agrégat : informations de base, compétences, langues, liens |
| `candidate/application/CandidateProfileService.java` | Lecture du profil complet, mise à jour avec contrôle de version |
| `identity/api/UserAccounts.java` + `identity/application/UserAccountsService.java` | Prénom et nom, qui vivent sur le compte |
| `candidate/web/CandidateProfileController.java`, `ProfileRequests.java`, `ProfileResponses.java` | HTTP et DTO |
| `candidate/web/CandidateWebMapper.java` | Mapping MapStruct entité → DTO (première utilisation) |
| Frontend `features/candidate/profile/components/basic-info-form.ts`, `data-access/profile.store.ts` | Formulaire et état de l'écran |

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| `version` obligatoire dans `PUT profile`, comparée à celle en base | Laisser le dernier écrire | Deux onglets ouverts : le second reçoit `409 CONCURRENT_MODIFICATION` au lieu d'écraser le premier |
| `@OptimisticLock(excluded = true)` sur les collections | Version incrémentée à chaque rubrique | Ajouter une compétence ne doit pas rendre obsolète le formulaire d'informations ouvert dans un autre onglet |
| Prénom et nom modifiés par `UserAccounts` (API du module Identité) | Accès direct à la table `app_user` | Spring Modulith interdit l'accès aux entités d'un autre module ; une seule transaction couvre les deux écritures |
| MapStruct pour les DTO de réponse, `unmappedTargetPolicy=ERROR` | Mapping écrit à la main partout | Code généré à la compilation, sans réflexion ; un champ de réponse oublié fait échouer le build. L'assemblage du profil complet reste écrit à la main (méthode `default`), car il combine trois sources |
| Valeurs vides enregistrées comme `NULL` | Chaînes vides | La complétude et les futurs filtres testent l'absence d'une seule façon |

## 4. Erreurs probables

| Symptôme | Cause | Solution |
| --- | --- | --- |
| 409 à chaque enregistrement | Le formulaire envoie une version ancienne | Le store envoie la version de la dernière lecture ; recharger après un 409 |
| Compilation : `Unmapped target property` | Nouveau champ de réponse sans source dans MapStruct | Ajouter la propriété à la source ou un `@Mapping` explicite |
| `LazyInitializationException` | Collection lue hors transaction | `ProfileView` est assemblée dans la transaction de lecture |

## 5. Questions d'entretien

**« Pourquoi ne pas demander l'âge ou la photo ? »** Ils n'aident pas à évaluer une compétence et exposent à la discrimination à l'embauche ; la loi et le RGPD imposent de ne collecter que le nécessaire.

**« Comment évitez-vous qu'un candidat lise le profil d'un autre ? »** L'URL ne contient aucun identifiant : `/candidates/me` lit l'identifiant dans le token. Pour les rubriques identifiées, chaque requête filtre sur le candidat connecté (`findByIdAndCandidateId`), et l'élément d'un autre répond 404, comme s'il n'existait pas.
