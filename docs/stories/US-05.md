# US-05 — Intégration continue minimale

Phase 2 · MUST · 2 points · dépend de US-01, US-04

## 1. Objectif et critères

| Critère d'acceptation | Comment |
| --- | --- |
| Tout push compile le backend et le frontend et lance leurs tests | `.github/workflows/ci.yml`, déclenché sur `push` (toutes branches) et `pull_request` vers `main` |
| Un test en échec rend la pipeline rouge et bloque la fusion | Chaque étape échoue au premier test rouge ; le blocage de fusion s'active dans GitHub (voir §3) |

## 2. Contenu de la pipeline

| Job | Étapes | Durée attendue |
| --- | --- | --- |
| Backend (Java 25) | `./mvnw verify` : tests unitaires puis d'intégration avec Testcontainers ; rapports téléchargeables en cas d'échec | 2 à 4 min |
| Frontend (Angular 22) | `npm ci`, ESLint, Prettier, Vitest, build de production | 1 à 2 min |

Les deux jobs tournent en parallèle. Un nouveau push sur la même branche annule l'exécution précédente. Les versions des actions (`checkout@v7`, `setup-java@v6`, `setup-node@v7`, `upload-artifact@v7`) ont été relevées sur leurs dépôts le 19 octobre 2026.

La pipeline va déjà au-delà du minimum demandé : les tests d'intégration du backend tournent aussi, car Docker est disponible sur les runners Ubuntu de GitHub.

## 3. À faire une fois dans GitHub

1. Générer et committer le wrapper Maven : `cd backend && mvn -N wrapper:wrapper`, puis `git add mvnw mvnw.cmd .mvn`. Sans lui, la pipeline utilise le Maven préinstallé du runner.
2. Pousser sur GitHub et vérifier que l'onglet **Actions** affiche les deux jobs en vert.
3. **Settings → Branches → Add branch ruleset** (ou *Branch protection rule*) sur `main` :
   - exiger une pull request avant fusion ;
   - exiger que les vérifications *Backend (Java 25)* et *Frontend (Angular 22)* passent ;
   - interdire les push directs sur `main`.

C'est cette règle qui rend une pull request rouge non fusionnable : la pipeline seule ne peut que signaler.

## 4. Erreurs probables

| Symptôme | Cause | Solution |
| --- | --- | --- |
| `./mvnw: Permission denied` | Bit d'exécution perdu (commit depuis Windows) | `git update-index --chmod=+x backend/mvnw` |
| `npm ci` échoue : lock file désynchronisé | `package.json` modifié sans `npm install` | Lancer `npm install` en local et committer `package-lock.json` |
| Job frontend rouge sur Prettier | Fichier non formaté | `npx prettier --write "src/**/*.{ts,html,scss}"` |
| Les vérifications n'apparaissent pas dans la règle de protection | La pipeline n'a encore jamais tourné | Pousser une première fois, puis revenir à la règle |

## 5. Questions d'entretien

**« Pourquoi la CI dès la phase 2 ? »** Pour qu'aucune régression ne passe inaperçue dès le premier commit. Ajoutée à la fin, elle découvre d'un coup des dizaines d'erreurs accumulées.

**« Que se passe-t-il si un test d'intégration est instable ? »** La pipeline devient rouge au hasard et l'équipe apprend à l'ignorer. Un test instable se corrige ou se met en quarantaine immédiatement, jamais en relançant jusqu'au vert.
