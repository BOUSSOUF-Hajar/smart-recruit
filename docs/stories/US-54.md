# US-54 — Lancer l'application en une commande

Phase 11 · MUST · 3 points · dépend de US-40 · réf. section 21 du prompt, E.4

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| `cp .env.example .env` puis `docker compose up` : frontend, backend, PostgreSQL et Ollama démarrent, l'application répond dans le navigateur | `docker-compose.yml` validé par `docker compose config` ; job `e2e` de la CI qui lance la pile exactement ainsi puis la parcourt avec Playwright ; vérifications locales décrites au §4 |
| Un service attend que ceux dont il dépend soient sains | `depends_on … condition: service_healthy` : backend → PostgreSQL, frontend → backend, `ollama-model` → Ollama ; health checks sur les quatre services (`pg_isready`, `/actuator/health/readiness`, `/healthz`, `ollama list`) |
| Aucun secret réel dans le dépôt | `.env` ignoré par Git ; `.env.example` ne contient que des valeurs marquées `local-demo-only` ; variables obligatoires sans défaut (`${JWT_SECRET:?…}`) ; analyse des secrets par Trivy en CI (US-55) |

## 2. Fichiers

- `docker-compose.yml` (4 services + `ollama-model`, réseau `internal`, volumes `pgdata`, `resumes`, `ollama-models`) ; `.env.example` réécrit.
- `backend/Dockerfile` (Maven puis JRE 25 Alpine, utilisateur `smartrecruit`, couches Spring Boot extraites, health check) ; `backend/.dockerignore`.
- `frontend/Dockerfile` (Node 24 puis `nginxinc/nginx-unprivileged`) ; `frontend/nginx/default.conf`, `frontend/nginx/security-headers.conf` ; `frontend/.dockerignore`.
- `application-prod.yml` : `server.forward-headers-strategy: native` (vraie adresse du client derrière Nginx).
- `angular.json` : `inlineCritical: false` en production (aucun script en ligne, CSP `script-src 'self'`).

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Nginx sert le frontend **et** relaie `/api` (même origine) | Backend exposé sur un second port, CORS | Pas de CORS ; le cookie de session `SameSite=Strict` restreint à `/api/v1/auth` fonctionne tel quel ; un seul port publié |
| Image Nginx non privilégiée (port 8080, uid 101) ; JRE sous un utilisateur dédié | Images par défaut en root | Un conteneur compromis n'a pas les droits root |
| Couches Spring Boot extraites (`jarmode=tools extract --layers`) | Jar unique | Une modification du code ne repousse que la couche `application` (quelques centaines de Ko) |
| Backend indépendant d'Ollama | `depends_on: ollama` | L'IA est facultative (RG-28) ; Ollama n'est même pas nécessaire en CI |
| Service `ollama-model` qui télécharge le modèle puis s'arrête | Téléchargement manuel documenté | « Une commande » pour tout ; l'application reste utilisable pendant le téléchargement |
| `forward-headers-strategy: native` | `framework` | La valve Tomcat ne croit `X-Forwarded-For` que venant d'une adresse privée : un client direct ne peut pas usurper son adresse dans l'audit |
| `inlineCritical: false` | CSP avec `'unsafe-inline'` pour les scripts | Une CSP stricte vaut plus que l'optimisation du premier affichage, mesurée négligeable ici |

## 4. Vérifications faites dans l'environnement de développement

L'environnement de ce dépôt n'a pas accès aux registres d'images (Docker Hub, ghcr.io, quay.io bloqués) : les images n'ont pas pu y être construites. Chaque morceau a été vérifié autrement :

| Élément | Vérification |
| --- | --- |
| `docker-compose.yml` | `docker compose config` (et échec explicite sans `.env`) |
| Dockerfiles | `hadolint` sans avertissement ; analyse syntaxique par BuildKit |
| Image backend | Couches extraites comme dans l'image, lancées avec `JarLauncher`, profils `prod,demo` et variables d'environnement du compose : démarrage, logs JSON, données de démo, adresse client lue dans `X-Forwarded-For` |
| Configuration Nginx | `nginx -t` puis Nginx réel devant le backend : retour à `index.html`, cache, en-têtes de sécurité, proxy `/api`, 413 au-delà de 6 Mo |
| Bout en bout | Suite Playwright (US-57) à travers ce Nginx, sans aucune violation CSP |

La construction réelle des images et le lancement par `docker compose` sont exécutés par la CI (jobs `e2e` et `images`).

### Validation sur un poste réel (phase 12, en cours)

Le 23 octobre 2026, sur un poste Windows 10 avec Docker Desktop 28.5 (4 CPU, 7,8 Go alloués à Docker) :

| Étape | Résultat |
| --- | --- |
| `cp .env.example .env` | Fait |
| `docker compose build` | **Échec réseau, pas de défaut du projet** : `TLS handshake timeout` vers Docker Hub pour `eclipse-temurin:25-jre-alpine` et `nginx-unprivileged:1.29-alpine` ; nouvelles tentatives de `docker pull` également en échec |
| Débit mesuré | 3,7 Ko/s depuis Maven Central, 7 Ko/s depuis npm : environ 1,5 Go d'images et de dépendances, plus environ 10 Go pour Ollama et le modèle, sont hors de portée sur cette connexion |

Aucune correction des Dockerfiles, de Nginx ni du compose n'a donc pu être déduite d'une exécution réelle. Une seule correction a été faite, à la lecture, à l'occasion d'US-58 : `location ^~ /api/` dans `default.conf`. Sans ce `^~`, la location des fichiers statiques, en expression régulière, interceptait tout chemin `/api/…` terminé par `.js`, `.css` ou `.png`. Aucun endpoint n'en avait jusque-là, mais Swagger UI sous `/api/docs` en a.

À reprendre avec une connexion correcte : `docker compose up --build`, santé des quatre services, connexion avec les comptes de démonstration, puis `npm run e2e`.

### Premier passage sur GitHub Actions (2 novembre 2026)

Premier push du dépôt (`main`, commit `e2cd776`) : la CI a fait ce que le poste de développement ne pouvait pas faire.

| Job | Résultat |
| --- | --- |
| Backend, frontend, Trivy (dépôt) | Verts |
| Bout en bout | **Vert** : images réellement construites, pile lancée par `docker compose up`, 5 tests Playwright passés à travers Nginx sans violation CSP |
| Images Docker (frontend) | **Rouge** : image construite, mais l'analyse Trivy de l'image trouve au moins une vulnérabilité critique corrigeable |
| Images Docker (backend) | Annulé par la matrice (`fail-fast`), donc jamais analysé |

Le détail de la vulnérabilité n'était lisible que dans le journal du job, réservé aux administrateurs du dépôt. Corrections (US-58) :

- `apk upgrade --no-cache` dans l'étape d'exécution des deux images : les images de base ont souvent quelques jours de retard sur les correctifs Alpine. Pour Nginx, on repasse root le temps de la mise à jour, puis `USER 101`. La règle hadolint DL3017 est ignorée explicitement à cet endroit, avec sa raison en commentaire.
- La CI construit et analyse désormais les images à chaque push, pas seulement sur `main` (voir [US-55](US-55.md)).

Second passage, sur la branche (commit `81ace27`) :

- **image frontend : verte**, `apk upgrade` a suffi ;
- **image backend : rouge**, et les nouvelles annotations ont nommé les vulnérabilités. Ce sont quatre CVE critiques de `tomcat-embed-core` 11.0.24, le Tomcat embarqué par Spring Boot 4.1.1 (CVE-2026-68525, CVE-2026-65905, CVE-2026-65637, CVE-2026-65182), corrigées en 11.0.25.

Correction : Spring Boot **4.1.1 → 4.1.2**, qui embarque Tomcat 11.0.27. Monter la version de correctif de Spring Boot plutôt que forcer `tomcat.version` garde un ensemble de versions testé ensemble.

Pourquoi l'analyse Trivy du dépôt (job « Dépendances et secrets ») ne l'avait pas vu : Tomcat n'est pas déclaré dans `pom.xml`. Il arrive en dépendance transitive, avec une version fixée par la nomenclature de Spring Boot, que Trivy reconstitue mal depuis le seul `pom.xml`. L'analyse de l'image lit les jars réellement embarqués : c'est la raison d'être de la seconde analyse.

## 5. Questions d'entretien

**« Pourquoi Nginx devant Spring Boot ? »** Pour servir les fichiers statiques efficacement (cache, compression), poser les en-têtes de sécurité à un seul endroit, garder une seule origine, et ne publier qu'un port. Le backend n'est joignable que sur le réseau interne.

**« Comment évitez-vous les secrets dans le dépôt alors que `cp .env.example .env` suffit ? »** Les valeurs du fichier d'exemple sont fictives et nommées comme telles ; elles suffisent pour essayer en local. Le profil `prod` n'a aucune valeur par défaut pour les secrets, et la CI cherche les secrets commités.
