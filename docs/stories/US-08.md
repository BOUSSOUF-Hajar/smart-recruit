# US-08 — Rester connecté

Phase 3 · MUST · 5 points · dépend de US-07 · réf. F-AUTH-03

## 1. Objectif et critères

Quand l'access token expire, le frontend le renouvelle sans bruit grâce au cookie ; chaque renouvellement fait tourner le refresh token, et un jeton rejoué ferme toutes les sessions.

| Critère d'acceptation | Preuve |
| --- | --- |
| Token expiré → renouvellement et rejeu invisibles | `refresh.interceptor.spec` : « renouvelle le token expiré puis rejoue la requête, sans notification » ; `AuthFlowIT.expiredTokenGetsASpecificCodeSoTheFrontendCanRefresh` |
| Ancien refresh token révoqué, nouveau émis | `AuthFlowIT.refreshRotatesTheTokenAndDetectsReuse` |
| Jeton **tourné** réutilisé → toutes les sessions révoquées, événement audité | même test ; action `TOKEN_REUSE_DETECTED` |
| (correctif phase 5) Jeton fermé par une déconnexion ou un changement de mot de passe → simple 401, les autres sessions restent ouvertes | `AuthFlowIT.closedSessionIsRefusedWithoutClosingTheOthers` ; migration V8 (`revocation_reason`) |
| Requêtes expirées simultanément → un seul renouvellement | `refresh.interceptor.spec` : « ne renouvelle qu'une fois » |

## 2. Fichiers

| Fichier | Rôle |
| --- | --- |
| `identity/application/AuthService.refresh` | Rotation sous verrou, détection de réutilisation |
| `identity/infrastructure/RefreshTokenRepository.java` | `findForUpdate` (`SELECT … FOR UPDATE`), révocations en masse |
| `shared/security/ApiAuthenticationEntryPoint.java` | `AUTH_TOKEN_EXPIRED` distingué de `AUTHENTICATION_REQUIRED` |
| Frontend `core/http/refresh.interceptor.ts` | 401 expiré → renouvellement → rejeu |
| Frontend `core/auth/auth.service.ts` (`refreshAccessToken`, `restoreSession`) | Renouvellement partagé, verrou Web Locks entre onglets |
| Frontend `core/auth/session-initializer.ts` | Restauration de session avant le premier affichage |

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Rotation à chaque renouvellement | Refresh token fixe 7 jours | Un jeton volé ne sert qu'une fois, et son usage trahit le vol |
| `@Transactional(noRollbackFor = AuthenticationFailedException.class)` | Transaction annulée par l'exception | Sinon la révocation de toutes les sessions serait annulée avec la requête |
| Verrou pessimiste sur la ligne du jeton | Verrou optimiste | Deux rafraîchissements simultanés sont sérialisés ; le second voit un jeton révoqué |
| Observable partagé (`shareReplay`) dans l'onglet + Web Locks entre onglets | Rien ; ou délai de grâce côté serveur | Évite les faux positifs de réutilisation sans affaiblir la règle serveur |
| Code `AUTH_TOKEN_EXPIRED` dédié | Tout 401 déclenche un renouvellement | Un token falsifié ne doit pas provoquer de renouvellement, mais une déconnexion |
| Ordre `[correlation, error, refresh, auth]` | Autre ordre | `error` ne voit que l'erreur finale ; la requête rejouée repasse par `auth` |

## 4. Erreurs probables

| Symptôme | Cause | Solution |
| --- | --- | --- |
| Déconnexion surprise avec deux onglets | Deux renouvellements simultanés sans verrou | Vérifier la prise en charge de `navigator.locks` ; sinon dernier recours : délai de grâce serveur |
| Boucle de renouvellements | Intercepteur appliqué à `/auth/refresh` lui-même | `isSessionEndpoint` exclut les endpoints de session |
| Notification « erreur » à chaque expiration | `error` placé après `refresh` | Respecter l'ordre de `app.config.ts` |
| Session perdue au rechargement en dev | Front servi sans le proxy | `npm start` (proxy `/api` → `localhost:8080`) |

## 5. Questions d'entretien

**« Que se passe-t-il si un attaquant vole un refresh token ? »** Il peut l'utiliser une fois. Dès que l'utilisateur légitime renouvelle avec le même jeton (déjà tourné), le serveur détecte la réutilisation, ferme toutes les sessions et l'audit le signale.

**« Pourquoi le rejeu passe-t-il par `next(request)` et pas par `HttpClient` ? »** Pour rester dans la chaîne au même niveau : `auth` réinjecte le token, et l'erreur éventuelle du rejeu remonte à l'appelant sans nouveau renouvellement.

## Correctif de la phase 5 : cause de révocation

En compilant et en exécutant réellement la suite en phase 5, un faux positif est apparu : un onglet resté ouvert après une déconnexion ailleurs présentait un jeton révoqué, et le serveur concluait à un vol en fermant **toutes** les sessions. La règle juste est plus étroite : seul un jeton **remplacé par rotation** qui revient prouve qu'une copie circule.

- V8 ajoute `refresh_token.revocation_reason` (`ROTATED`, `LOGOUT`, `PASSWORD_CHANGED`, `REUSE_DETECTED`, `ACCOUNT_DISABLED`) avec une contrainte qui la lie à `revoked_at`.
- `AuthService.refresh` : `wasRotated()` → révocation générale + audit ; autre cause → 401 `AUTH_REFRESH_INVALID` sans effet de bord ; compte désactivé → révocation `ACCOUNT_DISABLED`.
- Une nouvelle migration plutôt qu'une retouche de V3 : une migration publiée est immuable (Flyway vérifie les sommes de contrôle).

**Question d'entretien** : « Comment avez-vous trouvé ce bug ? » Par un test d'intégration qui enchaînait déconnexion puis renouvellement depuis un second appareil. Le cas n'était pas dans les critères ; il l'est désormais.
