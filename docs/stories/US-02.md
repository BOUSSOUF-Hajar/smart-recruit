# US-02 — Base de données versionnée

Phase 2 · MUST · 3 points · dépend de US-01

## 1. Objectif et critères

Brancher PostgreSQL 18 de façon reproductible : le schéma n'est créé que par des migrations Flyway, Hibernate se contente de vérifier, et les tests d'intégration tournent sur un PostgreSQL jetable.

| Critère d'acceptation | Statut | Preuve |
| --- | --- | --- |
| Base vide → migrations appliquées dans l'ordre, historique enregistré | Couvert | `DatabaseMigrationIT.allMigrationsAreAppliedInOrderAndRecorded` |
| Tests d'intégration sur un PostgreSQL éphémère, jamais la base de dev | Couvert | `TestcontainersConfiguration` + `@ServiceConnection` |
| Admin initial, catégories et entreprise de démonstration créés | **Déplacé** vers US-07, US-15 et US-56 (voir §2) | — |
| Profil `prod` : Hibernate valide le schéma sans le modifier | Couvert | `ProdProfileSchemaIT` |

## 2. Écart assumé : les données initiales

Le troisième critère contredit trois décisions prises ensuite dans la conception :

- l'**admin initial** n'est pas créé par une migration, qui ne peut pas lire un secret proprement, mais par `InitialAdminBootstrap` à partir de `INITIAL_ADMIN_EMAIL` et `INITIAL_ADMIN_PASSWORD` (Architecture Spring Boot §5) ;
- les **catégories** arrivent avec la migration des référentiels (roadmap, phase 4) ;
- l'**entreprise de démonstration** fait partie du jeu de données du profil `demo` (US-56), jamais d'une migration.

De plus, la roadmap fixe la règle « une table naît avec le code qui l'utilise » : en US-02, ni `app_user`, ni `job_category`, ni `company` n'existent encore.

Décision appliquée dans `docs/user-stories.md` (réversible si tu préfères autrement) : le critère est retiré d'US-02 et réparti entre US-07 (admin initial), US-15 (catégories et compétences de départ) et US-56 (données de démonstration).

## 4. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| `spring-boot-starter-flyway` + `flyway-database-postgresql` | `flyway-core` seul | Spring Boot 4 a sorti l'auto-configuration Flyway dans son propre module ; et depuis Flyway 10, le support de chaque base est un artefact séparé |
| `ddl-auto: validate` dans `application.yml`, donc pour tous les profils | `update` en dev | Un schéma modifié en dev par Hibernate diverge des migrations : le bug n'apparaît qu'en production |
| `open-in-view: false` | Valeur par défaut `true` | Évite les requêtes cachées pendant la sérialisation de la réponse et libère la connexion au plus tôt |
| `hibernate.jdbc.time_zone: UTC` | Fuseau de la JVM | RG-32 ; le pilote JDBC, lui, transmet le fuseau de la JVM à la session, d'où ce réglage explicite |
| Testcontainers + `@ServiceConnection` | H2 en mémoire, ou `@DynamicPropertySource` | H2 n'a ni `uuidv7()`, ni `unaccent`, ni `tsvector` ; `@ServiceConnection` écrit la connexion à notre place |
| Image `postgres:18-alpine`, même majeure qu'en dev et prod | `postgres:latest` | Un test doit tourner sur la version déployée, pas sur la dernière parue |
| Readiness = `readinessState` + `db` | Readiness par défaut | Une instance dont la base ne répond pas ne doit pas recevoir de trafic ; la liveness, elle, ne dépend pas de la base pour éviter des redémarrages en cascade |
| V1 = extension `unaccent` | Créer tout le schéma dès maintenant | La recherche sans accents en aura besoin ; les tables arrivent avec leur code |

## 5. Commandes

```bash
docker compose -f docker-compose.dev.yml up -d
docker compose -f docker-compose.dev.yml ps          # postgres doit être « healthy »

cd backend
./mvnw verify                                        # Docker doit tourner pour les *IT
./mvnw spring-boot:run
# Dans les logs : « Successfully applied 1 migration to schema "public", now at version v1 »

curl http://localhost:8080/actuator/health/readiness # {"status":"UP"}
docker compose -f docker-compose.dev.yml exec postgres \
  psql -U smartrecruit -c "select version, description, success from flyway_schema_history"
```

## 7. Erreurs probables

| Symptôme | Cause | Solution |
| --- | --- | --- |
| `Could not find a valid Docker environment` | Docker arrêté (ou Docker Desktop non démarré sous Windows) | Démarrer Docker, puis relancer `./mvnw verify` |
| `Connection to localhost:5432 refused` au `spring-boot:run` | Conteneur de dev non lancé | `docker compose -f docker-compose.dev.yml up -d` |
| `password authentication failed` | Volume créé avec un autre mot de passe | `docker compose -f docker-compose.dev.yml down -v` (efface les données de dev), puis relancer |
| Le conteneur postgres redémarre en boucle, message sur `/var/lib/postgresql/data` | Volume monté à l'ancien emplacement | PostgreSQL 18 attend le volume sur `/var/lib/postgresql` |
| `Validate failed: Migration checksum mismatch` | Un script déjà appliqué a été modifié | Ne jamais modifier un script appliqué : annuler la modification et créer `V2__...` |
| `Unsupported Database: PostgreSQL 18` | `flyway-database-postgresql` absent | Vérifier la dépendance dans le `pom.xml` |
| `Schema-validation: missing table [...]` | Une entité sans migration correspondante | Écrire la migration ; ne jamais passer en `ddl-auto: update` |

## 8. Questions d'entretien

**« Pourquoi Flyway plutôt que laisser Hibernate créer les tables ? »** Le schéma devient du code versionné et relu : chaque environnement applique les mêmes scripts dans le même ordre, et l'historique dit exactement où en est chaque base. `ddl-auto: update` ne supprime jamais une colonne, ne sait pas renommer, et ne laisse aucune trace de ce qu'il a fait.

**« Que se passe-t-il si tu modifies un script déjà appliqué ? »** Flyway enregistre une somme de contrôle par script. Au démarrage suivant, la validation échoue avec « checksum mismatch » et l'application refuse de démarrer. On corrige toujours par un nouveau script.

**« Pourquoi Testcontainers et pas H2 ? »** Un test sur H2 prouve que le code marche sur H2. Le projet utilise des fonctions propres à PostgreSQL (`uuidv7()`, `unaccent`, `tsvector`, JSONB, index partiels) : seule la vraie base les valide.

**« Que fait `@ServiceConnection` ? »** Spring Boot lit l'adresse, l'utilisateur et le mot de passe du conteneur démarré et les utilise à la place de `spring.datasource.*`. Plus besoin de `@DynamicPropertySource`, et aucun risque de pointer vers la base de développement.

**« Pourquoi désactiver `open-in-view` ? »** Activé, il garde la session Hibernate ouverte jusqu'à la fin de la réponse HTTP : un accès paresseux dans un mapper déclenche des requêtes invisibles, souvent en N+1, et monopolise une connexion. Désactivé, tout chargement est explicite dans le service.

**« Différence entre liveness et readiness ? »** La liveness dit « le processus est vivant » ; un échec entraîne un redémarrage. La readiness dit « je peux servir du trafic » ; un échec retire temporairement l'instance du répartiteur. La base est dans la readiness, pas dans la liveness : une panne de base ne doit pas faire redémarrer toutes les instances en boucle.
