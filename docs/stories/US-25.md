# US-25 — Rechercher des offres

Phase 5 · MUST · 8 points · dépend de US-23 · réf. F-JOB-04, RG-11, RG-19

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| « développeur » trouve « developpeur » et « Développeur » | `JobSearchIT.searchIgnoresAccentsAndCase` |
| Filtres combinés (ville, contrat, mode, niveau, compétence, salaire min.) | `filtersAreCombined` ; `searchParams` (spec) n'envoie que les filtres renseignés |
| DRAFT, CLOSED ou expirée jamais affichée | `draftsClosedAndExpiredOffersNeverAppear` |
| 20 par page, total, navigation ; taille > 100 ramenée à 100 | `resultsArePagedAndTheSizeIsCapped` ; `PageResponse.size()` ; paginateur Material |
| Champ de tri inconnu ignoré | `JobSortTest` (liste blanche `publishedAt`, `salaryMax`) |
| p95 < 800 ms sur 2 000 offres | Mesuré : **médiane 10,4 ms, p95 20,4 ms, p99 31,2 ms** (API réelle en jar, PostgreSQL 18, 2 000 offres, 200 requêtes filtrées variées) — scripts `backend/scripts/perf/` |
| (ajout) Un salaire masqué n'est ni affiché ni utilisable comme filtre | `hiddenSalaryIsNeverShownNorUsableAsAFilter` (sinon on pourrait deviner un salaire par dichotomie) |

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Plein texte PostgreSQL : `to_tsvector('french', immutable_unaccent(...))`, titre poids A, description poids B | `ILIKE '%…%'` ; Elasticsearch | Racinisation française et classement, index GIN ; aucun service de plus à exploiter |
| Colonne **générée** `search_vector` | Trigger ; calcul à la requête | Toujours synchrone, indexable ; PostgreSQL l'exige `IMMUTABLE`, d'où le wrapper `immutable_unaccent` (dictionnaire passé explicitement) |
| `plainto_tsquery` | `to_tsquery` | La saisie de l'utilisateur ne peut pas casser la syntaxe (`&`, `!`, parenthèses) |
| SQL natif avec `JdbcClient` et paramètres nommés | Criteria API / Specifications JPA | Requête dynamique lisible, `ts_rank`, `EXISTS` pour les compétences ; aucune entité à hydrater pour une liste |
| Tri par liste blanche (`JobSort`) | Champ de tri recopié dans le SQL | Aucune injection possible par `?sort=` |
| Compétences principales chargées en une 2e requête pour la page (`requiredSkills(ids, perJob)`) | Sous-requête par ligne | Évite le N+1 : 2 requêtes par page quel que soit le nombre de résultats |
| Filtres dans l'URL (`input()` liés aux paramètres de requête) | Formulaire en mémoire | Recherche partageable et rejouable (bouton retour) |

## 4. Commandes

psql -d smartrecruit -f backend/scripts/perf/seed-2000-jobs.sql

## 5. Erreurs probables

- `unaccent()` directement dans une colonne générée : refus « generation expression is not immutable ».
- Oublier `salary_visible` dans le filtre de salaire : fuite d'information.
- `count(*)` sur la requête triée : compter sur une requête sans `ORDER BY` ni `LIMIT`.

## 6. Questions d'entretien

**« Pourquoi pas Elasticsearch ? »** À 2 000 offres le p95 est de 20 ms ; un moteur dédié ajouterait une synchronisation et un service à surveiller pour un gain nul. Le seuil de bascule serait la recherche floue tolérante aux fautes ou des millions de documents.

**« Comment une offre expirée disparaît-elle sans batch ? »** Le filtre `expires_at > now()` fait partie de chaque requête publique, appuyé sur l'index `(status, expires_at)`.
