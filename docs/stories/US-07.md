# US-07 — Se connecter

Phase 3 · MUST · 5 points · dépend de US-06, US-52 · réf. F-AUTH-02, RG-03

## 1. Objectif et critères

Connexion par email et mot de passe : un access token JWT de 15 minutes dans le corps, un refresh token de 7 jours dans un cookie, et une trace d'audit pour chaque tentative.

| Critère d'acceptation | Preuve |
| --- | --- |
| Access token 15 min + cookie HttpOnly, Secure, SameSite=Strict, puis tableau de bord du rôle | `AuthFlowIT.loginReturnsATokenAndUpdatesLastLogin`, attributs du cookie vérifiés à l'inscription ; `LoginPage` spec (destination) |
| Mauvais mot de passe, email inconnu ou compte désactivé → même `AUTH_INVALID_CREDENTIALS` | `wrongPasswordUnknownEmailAndDisabledAccountGetTheSameAnswer` |
| Chaque tentative auditée | même test : raison `DISABLED` lue dans `audit_log` ; succès audité dans la transaction |
| Token : identifiant, rôle, entreprise si recruteur, rien d'autre | `JwtSecurityTest.tokenCarriesUserRoleAndCompany` |
| Admin initial créé au démarrage, mot de passe à changer | `InitialAdminBootstrap` ; flux du mot de passe temporaire testé par `temporaryPasswordMustBeChangedBeforeAnythingElse` |

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Resource server Spring Security + `NimbusJwtDecoder` | Filtre JWT écrit à la main | Validation éprouvée (signature, `exp`, `iss`, `typ`), aucune ligne de crypto maison |
| HS256 avec clé de 256 bits | RS256 | Un seul service émet et vérifie ; une paire de clés n'apporte rien ici |
| Access token en mémoire côté client | `localStorage` | Illisible par un script injecté ; la session revient au rechargement grâce au cookie |
| Hash factice comparé pour un email inconnu | Réponse immédiate | Même durée de réponse : on ne peut pas tester quels emails ont un compte |
| Échec audité en `REQUIRES_NEW` | Dans la transaction de connexion | L'exception annule la transaction ; la trace doit rester |
| `DelegatingPasswordEncoder` + `upgradeEncoding` | `BCryptPasswordEncoder` seul | Le préfixe `{bcrypt}` permet de changer d'algorithme et de rehacher à la connexion suivante |
| `companyId` dans le token | Lecture en base à chaque requête | Le contrôle de propriété des services n'a besoin d'aucune requête ; le token vit 15 min |

## 4. Commandes

```bash
# Créer l'admin initial en développement (valeurs par défaut dans application-dev.yml)
INITIAL_ADMIN_EMAIL=admin@smartrecruit.local INITIAL_ADMIN_PASSWORD='une-phrase-temporaire' ./mvnw spring-boot:run

curl -i -X POST localhost:8080/api/v1/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"admin@smartrecruit.local","password":"admin-temporaire-2026"}'
```

## 5. Erreurs probables

| Symptôme | Cause | Solution |
| --- | --- | --- |
| Démarrage refusé : `jwt.secret ... au moins 32 caractères` | `JWT_SECRET` absent ou court en prod | `openssl rand -base64 48` |
| 401 sur toutes les requêtes avec un token valide | En-tête `typ` absent ou émetteur différent | `JwtService` pose `typ: JWT` et `iss` ; ne pas fabriquer de token ailleurs |
| Démarrage refusé : `INITIAL_ADMIN_PASSWORD doit faire au moins 12 caractères` | Mot de passe initial faible | En choisir un plus long |
| Cookie absent dans le navigateur en HTTP | Attribut `Secure` | Passer par le proxy Angular (`localhost` est un contexte sécurisé) |

## 6. Questions d'entretien

**« Pourquoi deux jetons ? »** L'access token est court et sans état : s'il fuit, il expire vite. Le refresh token est long mais révocable, stocké haché en base, et voyage seulement dans un cookie inaccessible au JavaScript.

**« Pourquoi le même message pour un compte désactivé ? »** Sinon, l'API confirme qu'un compte existe. Seul l'audit distingue les cas.

**« Où mettez-vous le rôle ? »** Dans le claim `role`, converti en autorité `ROLE_…` par `JwtGrantedAuthoritiesConverter` ; `hasRole` l'utilise sans requête en base.
