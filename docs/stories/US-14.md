## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Entités rattachées par `candidateId`, avec leur dépôt | `@OneToMany` depuis le profil | Le contrôle de propriété est dans la requête (`findByIdAndCandidateId`) ; pas de collection à charger pour modifier un seul élément |
| Tri dans le domaine (`MOST_RECENT_FIRST`) | `ORDER BY end_date DESC NULLS FIRST` | Règle métier testée sans base ; JPQL n'a pas de `NULLS FIRST` portable |
| Contrainte de classe `@ChronologicalOrder` rattachée au champ de fin | Méthode `@AssertTrue` | L'erreur arrive sous le bon champ (`endDate`), pas sous un nom technique |
| Dates natives `<input type="date">` | Datepicker Material | Format ISO directement compatible avec l'API, sans adaptateur de dates |
| Confirmation avant suppression | Suppression immédiate | Action irréversible (architecture frontend §7) |

## 4. Questions d'entretien

**« Pourquoi valider l'ordre des dates à trois endroits ? »** Le formulaire pour le confort, le DTO pour refuser une requête mal formée avec un message par champ, la contrainte SQL comme garantie finale si un autre chemin écrivait en base.
