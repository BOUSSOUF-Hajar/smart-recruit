# US-40 — Brancher le service IA

Phase 8 · MUST · 5 points · dépend de US-01 · réf. D7.1, D7.3, architecture §6

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Aucune dépendance vers Ollama dans le code métier | `ModularityTest` (Spring Modulith) ; seul `ai/infrastructure/ollama` connaît Ollama, le reste dépend de l'interface `AIService` |
| `ai.enabled=false` → `AI_DISABLED`, boutons masqués | `AiDisabledIT` (503 `AI_DISABLED`, `GET /ai/status` → `enabled: false`, le workflow fonctionne) ; `AiPanel` spec |
| Ollama arrêté → application « UP », composant IA indisponible | `OllamaHealthIndicatorTest` : statut `UNKNOWN` (inférieur à `UP` dans l'agrégation) avec `available: false` et la raison |
| Les tests utilisent une fausse implémentation | `FakeAIService` (sources de test, `provider=fake`) : réponses fixes, dernier texte reçu conservé, pannes simulables |

## 2. Fichiers

`ai/application/AIService.java`, `AiProperties.java`, `AiException.java`, `Prompts.java` ; `ai/infrastructure/AiConfig.java`, `DisabledAIService.java`, `PromptLibrary.java`, `ollama/OllamaAIService.java`, `ollama/OllamaHealthIndicator.java` ; `src/main/resources/prompts/` ; `docker-compose.dev.yml` (service `ollama`) ; tests `OllamaAIServiceTest`, `OllamaHealthIndicatorTest`, `support/FakeAIService.java`.

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| `RestClient` vers `POST /api/chat`, schéma JSON dans `format`, température 0 | Spring AI | Un seul appel HTTP, lisible et testable ; `AIService` assure déjà la portabilité (architecture §6) |
| Implémentation choisie par configuration (`enabled`, `provider`) | Profils Spring | Le même binaire tourne partout ; un fournisseur inconnu fait échouer le démarrage au lieu d'échouer plus tard |
| Santé `UNKNOWN` quand Ollama manque | `DOWN` | `DOWN` rendrait toute l'application « DOWN » alors que l'IA est facultative (RG-28) |
| Adaptateur testé contre un faux serveur HTTP (`HttpServer` du JDK) | Appels à un vrai Ollama | Format des requêtes, nouvelle tentative, délais et pannes vérifiés sans modèle ni GPU |
| Modèle `qwen3.5:4b` sur `ollama/ollama:0.40.14`, épinglé le 4 novembre 2026 (provisoire `qwen3.5:9b` jusque-là) | Modèle figé sans mesure | Choisi par le banc d'essai ([résultats](../ai-model-benchmark.md)) : seul modèle mesuré qui remplit précision, rappel, CV piégé et temps |
| `think: false` envoyé à Ollama (`smartrecruit.ai.ollama.think`, vide : champ absent) | Laisser le modèle raisonner | Mesuré : avec le raisonnement, aucun CV n'aboutit en 300 s sur CPU ; sans, la précision reste à 0,98. Test `OllamaAIServiceTest` |
| Délai de lecture de 180 s pour un objectif de 120 s | Délai égal à l'objectif | Sur un processeur plus ancien, 4 CV sur 10 dépassaient 120 s : l'analyse asynchrone aurait échoué au lieu d'être lente |

## 4. Commandes

```bash
docker compose -f docker-compose.dev.yml up -d
docker compose -f docker-compose.dev.yml exec ollama ollama pull qwen3.5:4b
AI_ENABLED=true ./mvnw spring-boot:run
```

## 5. Questions d'entretien

**« Comment changeriez-vous de fournisseur ? »** Une nouvelle classe qui implémente `AIService` (appel HTTP, validation), une valeur de `provider` : rien d'autre ne change.

**« Pourquoi votre health check reste-t-il UP quand Ollama est arrêté ? »** Parce que l'IA est facultative. Le composant le dit (`available: false`), l'admin le voit, mais le load balancer ne doit pas retirer une application qui fonctionne.
