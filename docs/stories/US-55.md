# US-55 — Pipeline CI/CD complète

Phase 11 · MUST · 5 points · dépend de US-05, US-54 · réf. section 22 du prompt, ENF-SEC-11, ENF-SEC-12

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Pull request : compilation, tests unitaires, tests d'intégration (Testcontainers), analyse statique, couverture, dépendances vulnérables | `.github/workflows/ci.yml` : jobs `backend` (`mvn verify` + `spotbugs:check`), `frontend` (ESLint, Prettier, Vitest, typage e2e, build, `npm audit`), `security` (Trivy : dépendances et secrets), `e2e` ; fichier validé par `actionlint` |
| Couverture des services < 70 % → échec | `jacoco:check` dans `mvn verify`, sur les paquets `*.application` et `*.domain`, couverture unitaire + intégration fusionnée ; mesurée à **94,9 %** ; prouvé : relancé avec un seuil de 99 %, le build échoue |
| Fusion sur `main` → images construites et publiées | Job `images` (matrice backend, frontend) : construction, analyse Trivy de l'image (échec sur une vulnérabilité critique corrigeable), puis publication sur `ghcr.io/<dépôt>/<image>` avec les étiquettes `sha` et `latest` |

## 2. Analyse statique

SpotBugs (effort maximal, seuil moyen) a remonté 20 points au premier passage. Traitement :

| Constat | Nombre | Décision |
| --- | --- | --- |
| `NP_NULL_ON_SOME_PATH_FROM_RETURN_VALUE` (annotations `@Nullable` de Spring 7 : `encode`, `getSubject`, `health`) | 6 | Corrigé : non-nullité rendue explicite (`Objects.requireNonNull`, variable locale, cas `null` géré pour la santé d'Ollama) |
| `RV_ABSOLUTE_VALUE_OF_HASHCODE` (données de démo) | 1 | Corrigé : `Math.floorMod` |
| `DLS_DEAD_LOCAL_STORE` | 1 | Corrigé |
| `VA_FORMAT_STRING_USES_NEWLINE` (SQL construit par `formatted`) | 2 | Corrigé : substitution explicite plutôt que `String.format` |
| `CT_CONSTRUCTOR_THROW` (objets du domaine qui valident à la construction) | 10 | Exclu, motivé dans `spotbugs-exclude.xml` : choix de conception, `finalize()` dépréciée pour suppression |

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| Couverture unitaire **et** intégration fusionnée | Unitaires seuls | Les services sont surtout testés de bout en bout sur une vraie base ; le seuil mesure ce qui protège vraiment |
| Seuil sur `application` et `domain` seulement | Tout le code | Le cahier des charges vise les services et règles métier, pas la configuration |
| Trivy pour dépendances et secrets | OWASP Dependency-Check, Gitleaks | Un seul outil pour Maven, npm, secrets et images ; pas de clé d'API NVD à gérer |
| Image analysée **avant** publication | Analyse après coup | Une image avec une faille critique corrigeable n'arrive jamais dans le registre |
| `npm audit --omit=dev` | Audit complet | Seules les dépendances livrées au navigateur comptent pour la production |
| E2E sur la pile `docker compose` réelle | Serveur de développement Angular | Teste aussi les images, Nginx, la CSP et les health checks |

## 4. Limite

La pipeline n'a pas pu être exécutée sur GitHub depuis cet environnement (pas de dépôt distant). Chaque étape a été jouée localement : `mvn verify` avec le seuil, SpotBugs, `npm audit`, lint, tests, Playwright ; Trivy n'a pas pu télécharger sa base de vulnérabilités ici.

## 5. Question d'entretien

**« Une couverture de 95 %, c'est suspect ? »** C'est la couverture des lignes des services et règles métier par l'ensemble des tests, intégration comprise. Elle dit surtout qu'aucun chemin métier n'est oublié ; la qualité des assertions, elle, se voit dans les tests (scénarios d'erreur, concurrence, sécurité).
