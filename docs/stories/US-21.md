# US-21 — Créer une offre

Phase 5 · MUST · 5 points · dépend de US-10, US-15 · réf. F-JOB-01, RG-05, RG-20

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Offre créée en DRAFT, rattachée à mon entreprise, invisible du public | `JobOfferIT.newOfferIsADraftOfMyCompanyEvenIfAnotherCompanyIsSent` ; `JobSearchIT.draftDetailIsNotFound` |
| Entreprise envoyée ignorée, celle du token utilisée | Même test : le corps contient un `companyId` étranger, l'offre appartient à l'entreprise du recruteur |
| Salaire min > max ou compétence requise et souhaitée → champs en erreur | `invalidSalaryAndDuplicatedSkillAreFieldErrors` (`salary.max`, `preferredSkills[0].skillId`) ; `JobOfferLifecycleTest.salaryMinimumCannotExceedMaximum` ; validateurs `chronologicalOrder` et `uniqueBy` du formulaire |
| Catégorie désactivée → refus | `inactiveCategoryIsRefused` (`categoryId`) |

## 3. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| `companyId` absent du DTO, lu dans `CurrentUser` | Champ du DTO contrôlé par le service | Impossible d'oublier le contrôle : la donnée n'existe pas dans la requête (RG-05) |
| `JobContentValidator` appelle `CategoryCatalog` et `SkillCatalog` (API des autres modules) | Clés étrangères seules | Messages par champ (`requiredSkills[1].skillId`) au lieu d'une violation SQL ; les FK restent la garantie finale |
| Compétences dans `job_offer_skill` (`requirement`, `min_level` nul si PREFERRED, CHECK) | Deux tables | Une seule jointure pour le matching de la phase 8 |
| Salaire embarqué (`Salary`) avec visibilité | Table séparée | Toujours lu avec l'offre ; `salary_visible` décide de l'exposition publique |
| Formulaire unique création/modification, `FormArray` typés pour les compétences | Deux écrans | Mêmes règles, même code ; le mode est déduit de la route (`jobs/new` ou `jobs/:id`) |

## 4. Questions d'entretien

**« Et si un recruteur envoie `companyId` dans le JSON ? »** Jackson l'ignore (le DTO n'a pas ce champ) ; le test le prouve en envoyant volontairement une autre entreprise.

**« Pourquoi valider la catégorie dans le service si une FK existe ? »** La FK ne sait pas qu'une catégorie est désactivée, et elle produirait une erreur générique. Le service renvoie `VALIDATION_FAILED` sous `categoryId`.
