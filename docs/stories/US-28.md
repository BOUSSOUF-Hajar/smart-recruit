# US-28 — Suivre mes candidatures

Phase 6 · MUST · 3 points · dépend de US-27 · réf. F-APP-02, RG-23, cahier des charges D4.2

## 1. Objectif et critères

| Critère d'acceptation | Preuve |
| --- | --- |
| Offre, entreprise, date et libellé simplifié pour chaque candidature | `CandidateApplicationIT.candidateSeesSimplifiedStatusesAndNothingInternal` (liste et détail) ; `MyApplicationsPage` |
| SHORTLISTED → « En cours d'examen » | Même test (`IN_REVIEW`) ; `CandidateTimelineTest.everyInternalStatusHasACandidateLabel` |
| Rejet → « Non retenue », sans motif ni note, même dans la réponse brute | Même test : le JSON brut ne contient ni `REJECTED`, ni `SHORTLISTED`, ni le motif, ni le commentaire, ni `rejection` |
| (ajout) Pas de N+1 | `ApplicationListQueriesIT` : une page de 2 et une page de 20 font le même nombre de requêtes (candidatures, offres, entreprises, total) |

## 2. Choix techniques

| Choix | Alternative écartée | Raison |
| --- | --- | --- |
| `candidateStatus` calculé par le serveur (`CandidateStatus.of`) | Correspondance dans Angular | Sinon SHORTLISTED serait lisible dans les outils du navigateur (docs/api.md §5) |
| Types de réponse candidat et recruteur **séparés** | Une réponse commune avec des champs masqués | Un champ interne ajouté côté recruteur ne peut pas fuiter par sérialisation |
| Chronologie dédoublonnée (`CandidateTimeline`) | Toutes les entrées d'historique | SCREENING puis SHORTLISTED donneraient deux fois « En cours d'examen » |
| Liste assemblée par les API des modules (offres, entreprises) | Jointure SQL | Volume faible (ses propres candidatures) ; 3 à 4 requêtes fixes |

## 3. Question d'entretien

**« Comment prouvez-vous qu'aucune donnée interne ne fuit ? »** Le test lit la réponse **brute** et cherche les chaînes interdites. Un test sur les champs attendus ne verrait pas un champ en trop.
